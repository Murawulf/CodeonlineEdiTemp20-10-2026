1Contexte

L'application Codeonline EDI est déployée par pays (une instance par pays). Les échanges de documents EANCOM inter-pays doivent transiter par un Hub orchestrateur central (futur data registry), qui :

  • reçoit le message d'un pays émetteur sur POST /api/orchestrator/relay ;
  • résout le destinataire via son annuaire partners (clé = GLN) ;
  • relaie le message vers l'URL du destinataire (/api/edi/receive).

Au début de l'intervention, aucun échange CIV ↔ TUN ↔ SEN ne fonctionnait.

2Problèmes identifiés

P1 Collision de GLN (CIV = TUN)

CIV et TUN partageaient le même MY_GLN : 6191234567890. Identité émetteur ambiguë, routage impossible vers CIV.

P2 CIV absente de l'annuaire Hub

Aucune entrée pour la Côte d'Ivoire dans partners → tout message destiné à CIV renvoyait 404 Unknown recipient GLN.

P3 Authentification relais Hub → nœud (cause racine)

Le Hub n'envoyait qu'un x-api-pin. Or le middleware verifyJWT exige un Bearer JWT signé avec le JWT_SECRET partagé → tout relais renvoyait HTTP 401. Aggravant : le Hub n'avait ni JWT_SECRET, ni la dépendance jsonwebtoken.

P4 Chemin de stockage EANCOM non inscriptible (CIV)

EDI_ORDERS_PATH = /var/www/Edi-orders inexistant sur CIV, sans droits sudo → réception CIV en HTTP 500 (EACCES … mkdir).

P5 Base de données SEN vide

La base Dev_Entitedb du Sénégal ne contenait qu'1 table (ni Entite, ni app_parameters). Réception SEN en HTTP 500 (Table 'Dev_Entitedb.Entite' doesn't exist). Explique aussi les échecs SEN d'avril.

3Corrections appliquées

C1 GLN unique pour la Côte d'Ivoire

Attribution de 6181234567890 (préfixe GS1 Côte d'Ivoire = 618).

C2 Enregistrement de CIV dans l'annuaire Hub
INSERT INTO partners (gln, name, country_code, target_url, status)
VALUES ('6181234567890','Cote Ivoire Hub','384',
        'https://civ-dev.codeonline-edi.net/api/edi/receive','ACTIVE');
C3 Le Hub signe désormais un JWT de service (cause racine)

Modification de edi_orchestrator/services/routingService.js :

  • mint d'un JWT HS256 via le module natif crypto (sans ajouter jsonwebtoken) ;
  • en-tête Authorization: Bearer <token> ajouté à chaque relais ;
  • règle de routage par préfixe 618 → CIV (cohérence 619→TUN, SN→SEN) ;
  • ajout de JWT_SECRET (secret réseau) à edi_orchestrator/.env.

Token : { sub:'system', role:'service', instance:'hub' }, TTL 15 min. Sauvegarde routingService.js.bak.<ts> conservée sur le serveur.

C4 Chemin EANCOM inscriptible (CIV), résistant aux redéploiements
  • Paramètre CIV → /var/www/Edi-dev/backend/edi_orders (inscriptible) ;
  • init_db_params.js rendu surchargeable : process.env.EDI_ORDERS_PATH || '/var/www/Edi-orders' ;
  • env/.env.cote_ivoire : ajout de la surcharge → survit au prochain déploiement.
C5 Migration de la base SEN

mysqldump de TUN (82 tables, ~85 Mo) → chargement dans SEN avec FOREIGN_KEY_CHECKS=0 → 83 tables, 99 entités, 26 paramètres. Réécriture des paramètres propres à SEN : CURRENT_INSTANCE_CODE=senegal, MY_GLN=SN02583102G3, LOCAL_API_URL, EDI_ORDERS_PATH=/var/www/Edi-orders.

5Tests de bout en bout (validation)

Documents testés : ORDERS et INVOIC. Chaque message envoyé au Hub (POST /api/orchestrator/relay), puis vérification : (1) statut DELIVERED au journal Hub ; (2) persistance chez le destinataire (edi_transmissions, INBOUND).

DocumentCIV→TUNTUN→CIVTUN→SENSEN→TUNSEN→CIVCIV→SEN
ORDERS✅✅✅—✅—
INVOIC—✅—✅—✅

Les 3 paires de pays sont couvertes, dans les deux sens, pour les deux types de documents. Tous les messages : DELIVERED au Hub + persistés chez le destinataire.

Preuves de persistance — TUN : ORDERS reçu de CIV (6181234567890) · CIV : ORDERS reçu de TUN (6191234567890) · SEN : ORDERS reçu de TUN + INVOIC reçu de CIV.

7Points en attente / recommandations

#PointPriorité
1Versionner le Hub. Le code edi_orchestrator/ n'est pas sous git — à intégrer au dépôt principal. Le correctif mint-JWT devra y être commité (sauvegarde .bak sur serveur).important
2Chemin de réception CIV. Solution durable sans sudo en place. Alternative propre : créer /var/www/Edi-orders (droits consultant) pour s'aligner sur TUN/SEN.option
3Sécurité du relais. Les nœuds acceptent tout JWT signé avec le secret partagé. Durcir : valider le claim instance:'hub', restreindre l'IP source, ou mTLS.important
4Chemin chiffré non testé. /api/p2p/receive (RSA) non validé — nécessite l'échange des clés publiques entre CIV/TUN/SEN.à planifier
5Autres types EANCOM. ORDRSP, ORDCHG, DESADV, IFTSTA empruntent le même chemin (routage GLN + parseEANCOM) — testables sur demande.option
6Provisionnement nouveau pays. SEN n'avait jamais été migré. Vérifier que le process d'onboarding inclut bien migration schéma + données avant mise en service.important
